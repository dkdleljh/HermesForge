# HermesForge 프로젝트 종합 분석 보고서

## 1. 🏛️ HermesForge 코드베이스 분석 보고서

HermesForge 프로젝트의 핵심 디렉토리(`backend`, `frontend`, 설정 파일)를 탐색한 결과를 바탕으로 코드베이스 아키텍처 및 철학을 정리한 분석 내용입니다.

### 1.1 🎯 프로젝트 철학 및 목적
HermesForge는 단순한 사건/사실 저장소가 아닌 **'가능역(Possibility Field) 엔진'**입니다. 
게임, 교육, 훈련, 정책 실험 등에서 "무엇이 일어날 수 있는가?"를 탐구하고 시뮬레이션하기 위해 설계되었습니다.
가장 큰 특징은 사실과 허구를 명확히 분리하기 위한 **Safety Kernel**과 시스템 전반에 적용되는 **`NOT_FACT` 워터마크** 메커니즘을 강제한다는 점입니다. 이는 생성된 시나리오가 오남용되는 것을 방지합니다.

### 1.2 💻 기술 스택 (Tech Stack)
현대적인 **Python 백엔드 + React 프론트엔드** 조합으로 구성되어 있습니다.

* **Backend (Python 3)**
  * 프레임워크: `FastAPI` (비동기, 고성능 API 처리)
  * 데이터/검증: `Pydantic` v2 (엄격한 타입/스키마 검증)
  * 테스트: `pytest`
  * 서버: `uvicorn`
  * 저장소: 기본 SQLite (`hermesforge.db`)로 구성된 것으로 보이며 PostgreSQL 등 외부 DB로 확장이 가능하도록 추상화되어 있습니다.
* **Frontend (React)**
  * 언어/빌드: `TypeScript`, `Vite`
  * 상태/데이터 페칭: `@tanstack/react-query` (서버 상태 동기화 최적화)
  * 스타일링: `TailwindCSS`

### 1.3 🧩 핵심 도메인 개념
비즈니스 로직은 다음과 같은 5가지 핵심 파이프라인으로 동작합니다.
1. **Evidence**: 입력되는 기초 단서나 사실 조각.
2. **LambdaPatch (Λ-patch)**: Evidence를 바탕으로 특정 조건에서 어떤 결과가 나올지 정의한 "가능성 규칙".
3. **Snapshot**: 특정 시점에 존재하는 Evidence와 Patch들의 묶음.
4. **Context**: 현재 렌더링을 요청하는 사용자 권한, 환경, 의도 등 외부 조건.
5. **RenderedEvent**: Snapshot과 Context가 결합하여 산출된 "가능한 결과(항상 `POSSIBILITY_RENDER`를 반환)".

### 1.4 📂 디렉토리 구조 및 아키텍처 패턴
프로젝트는 유지보수성과 확장성을 위해 각 모듈의 역할이 뚜렷하게 나뉜 구조를 취하고 있습니다.

* **백엔드 (`backend/app/`) - 도메인 주도 설계(DDD) 및 Layered Architecture**
  * `api/`: FastAPI 라우팅 및 컨트롤러. 외부 HTTP 요청을 처리합니다.
  * `core/`: 전역 설정, 예외 처리, 데이터베이스 초기화 등 코어 컨피그.
  * `domain/` & `models/`: 핵심 비즈니스 로직 모델, 엔티티.
  * `schemas/`: Pydantic을 이용한 DTO (요청/응답 데이터 검증).
  * `engine/`: Snapshot을 기반으로 Context를 주입해 RenderedEvent를 생성하는 시뮬레이션 코어 파트.
  * `policies/`: **Safety Policy**. `NOT_FACT`를 강제하고 권한을 통제하는 정책 규칙 엔진.
  * `plugins/`: 교육, 게임, 훈련 등 특정 도메인을 위한 확장 플러그인을 담는 공간.
  * `repositories/`: 데이터베이스 접근을 캡슐화한 저장소 계층 패턴.
  * `services/`: API와 Repository 사이의 복잡한 비즈니스 로직 수행.

* **프론트엔드 (`frontend/src/`) - Feature-Sliced Design / 모듈식 구조**
  * `app/`: 전역 설정 및 앱 진입점 (Router, Providers).
  * `features/`: 도메인 단위(예: Snapshot, LambdaPatch 등)로 묶인 컴포넌트, 상태, 훅의 집합.
  * `components/`: UI 위주의 재사용 가능한 공통 컴포넌트.
  * `services/`: 백엔드 API와의 통신 로직.
  * `hooks/`: React Query를 활용한 커스텀 데이터 페칭 훅.

## 2. 💡 정확하게 뭘 하는 프로그램인가? (직관적 설명)

쉽게 말해 이 프로그램은 **"만약에 ~한다면 어떻게 될까? (What if?)"를 안전하게 시뮬레이션해 주는 '시나리오 생성 엔진'**입니다.

과거에 일어난 **'사실(Fact)'을 기록하는 일반적인 데이터베이스가 아닙니다.** 주어진 단서와 조건들을 조합해서 **'일어날 법한 결과(Possibility)'를 만들어내는 프로그램**입니다. 

### ⚙️ 어떻게 작동하나요? (3단계)
요리에 비유하자면 다음과 같습니다.
1. **단서 (Evidence) = 재료**: "현재 온도는 30도다", "주인공은 검을 가지고 있다" 같은 기본 사실들입니다.
2. **규칙 (LambdaPatch) = 레시피**: "만약 온도가 30도일 때 비가 오면, 습도가 매우 높아진다" 같은 인과관계 규칙입니다.
3. **상황 (Context) = 요리하는 환경**: "이 결과를 보는 사람이 초등학생인가, 전문가인가?", "현재 상황이 밤인가 낮인가?" 등의 맥락입니다.

프로그램은 이 세 가지를 조합해서 **"이러이러한 상황에서는 이런 결과가 벌어질 것이다(RenderedEvent)"**라는 시나리오를 계산해서 보여줍니다.

### 🎯 구체적으로 어디에 쓰나요?
1. **게임 및 인터랙티브 스토리텔링 (TRPG 등)**
   * **상황**: 플레이어가 보스 몬스터와 싸우고 있습니다.
   * **작동**: 시스템은 플레이어의 과거 행동(단서)과 스킬 규칙(Patch)을 계산해 실시간으로 렌더링해서 게임에 반영합니다.
2. **재난 대응 훈련 및 교육**
   * **상황**: 소방 지휘관 훈련 시뮬레이터
   * **작동**: "A공장에 화재가 났고, 바람이 남동풍으로 분다"는 상황에서 특정 선택을 했을 때 불길이 어떻게 번질지 예측된 시나리오를 훈련병에게 보여줍니다.
3. **정책 실험 (디지털 트윈)**
   * **상황**: 시청에서 새로운 교통 정책을 도입하려 합니다.
   * **작동**: 현재 도시의 교통량 데이터에 새로운 규칙을 적용하면 어떤 일이 벌어질지 가상으로 결과를 뽑아봅니다.

### 🛡️ 'NOT_FACT(사실 아님)' 워터마크의 중요성
이 엔진이 만든 시나리오를 누군가 진짜 뉴스로 악용하는 것을 막기 위해, 시스템 자체적으로 **"이것은 실제 일어난 일이 아니라, 엔진이 만들어낸 가상의 시나리오일 뿐입니다(NOT_FACT)"**라는 꼬리표를 강제로 붙여서 가짜 뉴스나 오해로 번지는 것을 시스템 구조적으로 막습니다.

## 3. 🎲 실제 현실과 몇 %가 일치하는가?

이 프로그램이 현실과 "몇 퍼센트(%)" 일치하는지는 결론부터 말씀드리면 **"고정된 수치가 없습니다."** 
오히려 정확한 대답은 **"사용자가 얼마나 정확한 데이터(단서)와 촘촘한 규칙(패치)을 이 프로그램에 입력해 주느냐에 따라 0%에서 99.9%까지 달라진다"**입니다.

이 프로그램 자체는 내용물의 "진짜/가짜"를 판별하는 인공지능이 아니라, **수학적인 "시뮬레이터 계산기(Engine)"**에 가깝습니다.

### ⚙️ 프로그램이 현실 가능성을 계산하는 원리
내부 코드를 보면 `LambdaPatch`(규칙) 항목에 3가지 핵심 수치가 곱해져서(score) 결과의 현실성을 계산합니다.
1. **`probability_mass` (발생 확률)**: 이 규칙대로 사건이 벌어질 수학적 확률입니다.
2. **`confidence` (신뢰도)**: 이 규칙 자체를 얼마나 믿을 수 있는지 나타내는 수치입니다.
3. **`anchor_weight` (상황 가중치)**: 현재 주어진 특수한 상황(Context)에 이 규칙이 얼마나 잘 들어맞는지 부여하는 가중치입니다.

### 🔄 모드에 따른 결과물 차이
프로그램은 `deterministic`(단 1개의 결과만 확정적으로 보여주는 모드)과 `weighted`(여러 가능성을 확률 비중에 따라 다양하게 보여주는 모드)를 제공합니다.

* **10%의 현실 (나쁜 예)**: "주인공이 검을 휘두르면 몬스터가 무조건 죽는다"처럼 비현실적이고 단순한 데이터만 입력해두었다면, 출력되는 시뮬레이션 결과는 현실과 전혀 맞지 않는 판타지가 됩니다.
* **90% 이상의 현실 (좋은 예)**: 교통 공학자가 "10년간의 비 오는 날 출근길 교통량 데이터"와 "수리 통계적 지연 확률"을 촘촘하게 입력해두었다면, 렌더링 결과는 실제 현실의 교통체증과 매우 유사하게 맞아떨어질 것입니다.

**💡 요약**: 이 프로그램은 현실을 알아맞히는 마법의 구슬이 아니라, 사용자가 입력한 데이터와 확률 규칙을 오차 없이 계산해 '가장 일어날 법한 결과물'을 조립해 주는 똑똑한 공장(Forge)입니다. 재료가 정확할수록 현실과의 일치율은 무한히 올라갑니다.
